# Zvec 只读全文索引修正验证

2026-10-17，在 Mate 90 Pro Max（CMM-AL10）上，通过独立测试包验证。基于 Zvec v0.7.0 及既有 OHOS 平台补丁，提取上游 [PR #770](https://github.com/alibaba/zvec/pull/770) 的只读 memtable 调整。参照提交 f137026994a997d5c8d4e8d4915f0eff2218a58c；该 PR 尚未合并。

只读 FTS 上下文改为普通跳表，可写上下文仍使用 HashSkipListRepFactory 和 1,000,000 桶。未引入共享缓存、写缓冲预算或可写桶数调整；索引格式与公开 C API 不变。

## 构建

新补丁只修改 rocksdb_context.cc/.h。build_zvec_ohos.ps1 按序应用平台补丁和只读补丁，并分别检查是否已应用。独立影子目录已通过补丁正向应用与重复构建所需的反向检查，PowerShell 语法检查通过。

验证库不带诊断插桩。复用原 Release 的依赖和未改动对象，只重编改动源文件并重链接。对照库使用原始对象重链接；仅为让两库在同一 HAP 中分别加载而调整文件名与 SONAME。两者的 380 个动态导出符号与原版一致，没有添加诊断接口。原始源码工作目录、静态归档和公开动态库不改动。

## 检索与内存

使用同一批 T2Retrieval 固定子集：20,000 篇文档、500 条查询，共享 Jieba-rs 0.8.1 默认模式加 HMM 预分词结果，whitespace 索引，普通词项显式 OR，Top100。一次查询直接通过公开 C API 返回正文，再由共同的 Native 测试模块整理和编码 JSON。

每格两个独立进程，每进程 500 次预热并逐条核对，随后两轮各 500 条计时查询。共 16 次主对照进程、16,000 条预热后时延记录；第二轮配置顺序反转。只有指定引擎被加载，手机端输入哈希一致。

PSS 是实际驻留页按共享比例分摊的内存。表中均为相对本进程加载引擎前的增量，单位 MiB，取两次进程的平均值；并非整个进程的绝对内存。

| 索引 / 集合模式 | 原版打开后 | 修正版打开后 | 原版查询后 | 修正版查询后 |
| --- | ---: | ---: | ---: | ---: |
| 已优化 / 只读 | 158.22 | 74.14 | 174.14 | 89.38 |
| 未优化 / 只读 | 132.01 | 78.56 | 144.77 | 91.69 |
| 已优化 / 读写 | 159.04 | 128.47 | 173.86 | 144.34 |
| 未优化 / 读写 | 132.68 | 132.74 | 145.79 | 145.51 |

已优化索引以读写模式打开时，封存段仍按只读恢复，因此也有收益；实际可写段保持原来的百万桶配置。未优化读写条件的内存基本一致，RocksDB 写出的 OPTIONS 中桶数也仍为 1,000,000。

| 索引 / 集合模式 | 原版 P50 / P95 ms | 修正版 P50 / P95 ms |
| --- | ---: | ---: |
| 已优化 / 只读 | 2.434 / 5.489 | 2.372 / 5.387 |
| 未优化 / 只读 | 10.541 / 31.043 | 10.658 / 31.588 |
| 已优化 / 读写 | 2.269 / 5.503 | 2.203 / 4.981 |
| 未优化 / 读写 | 11.519 / 34.528 | 11.509 / 34.592 |

P50/P95 表示 50%/95% 的查询耗时不超过该值。时延包括查询、结果整理和完整 JSON 编码，不含主机分词及写报告。未固定 CPU 频率、未清系统缓存，每格仅两个进程，不能把小幅差异解释为确定的加速或零成本。

同一索引状态下，两种库和读写模式的 500 条查询，完整 Top100 ID 顺序与分数逐项一致，正文与冻结语料一致。该结论不要求不同索引状态之间的浮点分数完全相同。

## 持久化与重复打开

另用两个独立索引副本分别完成四阶段测试：写入 1,000 条真实语料文档并 flush、只读重开、更新删除、再次只读核验。每阶段为独立进程，第一轮原版写入、修正版读取和更新、原版最终核验；第二轮反向，共八个阶段，全部通过。

核对全部新增文档的独特查询与正文。更新阶段替换一条、删除一条、再新增一条，旧词消失、新内容和保留文档正确。只读 upsert/delete 被拒绝，记录不变。这同时覆盖封存段与新增可写段共同存在的索引。

八个只读查询进程各补充五轮打开、20 次查询、关闭。分配器 allocated_bytes 的第五轮减第一轮介于 -187.83 KiB 与 +104.13 KiB，未见持续增长。该观察不将分配器保留页等同于泄漏，也不代替长期压力测试。

## 查询语法补充

两轮分别由原版和修正版写入五条英文、中文位置样本，再由另一套库在新进程中只读打开。每阶段九条查询，核对完整 ID 集合、正文和分数有效性，四个阶段共 36 条断言，全部通过。覆盖 AND、OR、上游二元 NOT 语法和中英文正反词序的双词短语。

补充阶段使用的两套引擎库与主对照哈希相同，只扩展测试模块。全部验证共 28 次独立进程运行。测试结束后停止独立测试包；没有接入聊天 App、切换其模型或操作其他 Session 的实验。

## 验证范围

本次针对 v0.7.0 的只读全文索引路径，不包含向量或混合检索、断电恢复及长期压力测试。未更改分词规则，没有接入聊天 App。补丁位于 [zvec-0.7.0-fts-readonly.patch](../patches/zvec-0.7.0-fts-readonly.patch)，源码构建会应用它；`v0.7.0-ohos.2` 预编译包包含这项修正，`ohos.1` 保留供回退。

## 最终预编译包复核

`v0.7.0-ohos.2` 从固定版本的干净源码和空构建目录完成全量交叉编译，并通过重复构建。最终库保留正式名称和 SONAME `libzvec_c_api.so`，380 个动态导出符号与旧版一致，动态依赖仍为 `libc++_shared.so` 和 `libc.so`。

该库以原始字节打包进独立签名 HAP，在同一 Mate 90 Pro Max 上完成八次进程运行：原有 C API 三轮生命周期、standard/ngram 全文检索的三阶段 30 条断言、两种索引状态各 500 条真实查询，以及两组各九条布尔与中英文短语断言。全部通过，真实查询的完整 Top100 ID 顺序与分数与原版一致，正文与冻结语料一致。
